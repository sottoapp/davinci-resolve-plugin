# Review and feedback

The test of an edit isn't technical elaboration: does the audience understand the story, feel the intended emotion,
and never notice an edit unless noticing is the point?

## Internal review
Watch straight through without stopping: picture only · sound only · at normal speed · muted · full screen · on a
phone. Write **timecoded** notes and classify each: **Story** (motivation, context, ending) · **Performance** (take,
reaction) · **Rhythm** (slow/rushed/repetitive) · **Continuity** (geography, eyeline, props, direction) · **Sound**
(noise, level, sync, transitions) · **Image** (exposure, colour, reframing, graphics) · **Technical** (titles,
captions, glitches, spelling, export). Add Resolve **markers** (colour = category) so notes live on the timeline.
For a built cut, run the `cut-reviewer` agent — it judges frames, not metadata.

## External review
Brief reviewers: "Where did you lose interest?" "What did you think this scene was about?" — not "did you like it?"

## Applying notes
Separate **preference** from a real **comprehension** problem · group duplicates · fix structural notes before
cosmetic ones · change one thing at a time when diagnosing · re-watch the sequence before editing defensively ·
audiences detect *that* something fails but not *why* (look upstream for missing setup).

## Versioning in Resolve
Duplicate the timeline before each round (`07_TIMELINES`, dated names), never overwrite an approved cut, export a
clearly named version per round, and keep a notes doc: what changed, what is unresolved. Picture lock before finishing
(`resolve-guide-project-media`, `resolve-qc-gate` before delivery).
